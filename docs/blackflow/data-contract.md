## 开局奖励候选证据（v1.1.12，2026-09-23）

自动采集在每次开局奖励标题 OCR 后、点击前新增 `start.reward.candidates` 事件，
保存同一次 OCR 的原图及全部结果，不过滤未选中的奖励或无法归一的文字。
`details.candidates` 按原始顺序记录 `detected_index`（从 0 开始）、`text`、`score`、
`rect`（x、y、width、height）和 `canonical`（无法可靠归一时为 null）；
`candidate_count` 是 OCR 框数量，`recognition_scope=visible_title_roi`，
`recognition_status` 为 `titles_detected` 或 `no_titles`。这是标题区域的部分识别，
不保证游戏中所有可选奖励均已识别；空结果与旧日志缺失都不能当作奖励不存在。

`planned_selection` 只表示本次准备点击的候选；现有流程确认选中后，另写
`start.reward.selected`（`phase=completed`、`outcome=confirmed`），携带
`selected_index`、`selected_name` 和 `preferred`。两类事件通过本局递增的
`observation_index` 关联，重复选择或重试分别留证。原有 `start_rewards` 继续仅
记录已确认选择，不改变选择优先级、确认点击或其他模式，不额外运行 OCR。
图片使用既有事件图片路径和完整性登记，传入原识别帧，不再等待或重新截图。

这些是 schema 1 的可选事件，原始契约、归档和签名版本均保持 1。同一批生产分支回放
生成的合成样本 `unit_test/fixtures/BlackFlow/start-reward-events.json` 同时用于独立
签名验证和 analysis 兼容测试。现有 analysis 原样保留为 `reward_evidence`，
不新增 OCR 任务，也不会把未选中的候选计入奖励获得数；验证器、专题统计、机器人及
同步插件无需代码变更。新字段可用于后续候选分析，候选出现次数和实际获得次数须分开。
旧包继续兼容，未知版本仍拒绝；旧数据、缓存、人工审核及冻结报告不自动改写。
本地 Core 编译、352 项 C++ 用例、27 项交互回放和 4 项归档／消费者兼容测试通过；
其中 7 项开局奖励回放覆盖候选留存、确认失败、空识别、未知文字、多次选择和无日志观察器。
旧实现运行相同回放时 6 项候选证据检查失败。相关回放已并入现有交互测试与发布 CI，
尚无新版实机完整对局验证；本次发布目标为 v1.1.12，包与渠道以发布流水线结果为准，未更新运行实例。

## 新增的原始契约声明

manifest 新增 `run_uuid`（UUID v4）、`contract_id/version`、`archive_schema_version`、`image_layout_version`、`capabilities`、`coverage=observed-events-only`。采集模式来源为 `event.state.profile`。当前没有资源文件内容摘要，因此 `resource_identity=not-recorded`，不假定同程序版本使用相同资源。能力声明只表示支持记录某种证据，不证明每层都有观测。

`python tools/BuildBlackFlowContract.py --output OUTPUT` 导出原始契约描述、独立验证器、真实 C++ 封包样本、预期验证结果及逐文件摘要。Windows 包和 macOS DMG 打包流程已调用此入口。bundle 记录来源 commit 与相关源文件是否未提交；dirty 导出不是已发布上游版本。analysis 固定 bundle 摘要后随包分发，不在机器人中复制验证器。

验证器退出码：0 本地签名/内容通过；1 损坏；2 未签名/旧版/重打包；3 未支持契约；4 缺少依赖。旧版兼容解析仍须经过路径、大小、版本和事件检查。

更新封包或必要成员时，同时检查消费者限制。已核对的机器人默认上限是压缩包 256 MiB、10,000 成员及 2 GiB 解压量；当前独立验证器上限不同。限额是部署条件，不能靠新包内容自动抬高宿主上限。

## 修改采集程序时的检查范围

新增/删除/改名字段、改变事件触发时机、修改图像位置或分辨率、改变地图/楼层身份、实际消耗判定、精简日志、快跑模式、封包和哈希/签名规则，都需要检查下游验证、处理和分析。程序功能或性能修改若不影响这些输出，记录无数据契约影响的理由即可。

对受影响变更：

1. 用最小输入说明前后区别，更新生产者测试样本与预期业务含义。
2. 联动本仓库独立验证器和原始契约，再更新 analysis 的版本适配、标准事实和受影响专题。检查三层专用记录、完整对局和未到达楼层的差异。
3. PtilopsisBot 与 quark-timed-sync 的业务逻辑放在 analysis 插件；只有宿主钩子/协议/通用传输能力变化才修改宿主核心。
